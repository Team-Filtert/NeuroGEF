GAME STATE

All runtime state lives on the GameState autoload.

```
# Rough shape
extends Node

var party: Party            # Live data container for the current party.
var inventory: Inventory    # Live data container for the inventory.
var keys: PersistenceKeys   # Persistent flags, counters, chests, NPCs talked to, ...
var quests: QuestManager    # Started quests, keyed by id.
```

GameState is also the scene-flow owner: states are pushed and popped onto a stack
(GameState.push(path), GameState.pop(result)) and it owns the transition root.

The state containers (Party, PartyMember, Inventory, QuestManager, ...) are plain data
plus helpers, and each one is meant to be serialized through its to_dict()/from_dict()
methods so saving and loading is a matter of walking them.

SCENE CHANGING AND TRANSITION EFFECTS

LevelManager owns the level root and PlayerManager owns the player. Changing a level
loads the new scene, finds the SpawnPoint matching the requested spawn id, and asks
PlayerManager to position and face the player through its methods. The player lives on
its own PlayerRoot, separate from LevelRoot, so it survives level swaps and is only
repositioned. Transitions are BaseTransition scenes played around the change.

PARTY STATE

Party members are data driven through CombatantData/PartyMember resources: name, stats,
battle visuals and attacks.

This is what lets the player be different characters with a different skin/sprite, name
and stats. That means the same data is in charge of both combat visuals AND overworld
visuals, so keep both in mind:

```
var battle_visual: Texture2D
var overworld_visual: Texture2D
```

THE PLAYER

The player is separate from levels on the tree, on its own PlayerRoot node separate from
LevelRoot, and is repositioned when needed, so it always stays on the tree while in
gameplay.

The class itself is dumb and just helps with visuals.

If something external ever needs a reference to the player, that's coordinated through
PlayerManager methods (E.G.: PlayerManager.get_player_position(),
PlayerManager.set_player_position(), PlayerManager.set_player_facing()), NEVER directly.


THE OVERWORLD PARTY

The party walks as a line. PlayerManager spawns the leader and one follower per extra
GameState.party member (party[1..]). The leader keeps a short position history and each
follower trails it at a fixed distance (characters/playable/party_follower.tscn), so the
party snakes along the leader's path. Followers share the leader's active state: they are
parked (physics off) whenever the leader is, e.g. during combat or dialogue.

The leader is always party[0]; giving a different member the lead just means reordering
GameState.party.members and respawning the player.


QUEST SYSTEM

Quests are data driven resources under `res://states/quests`. A Quest has an id, name,
type, a description and a root goal tree.

A goal tree is built out of QuestNode subclasses:

- PersistenceGoal
  Completes when a persistence key holds an expected value. Most goals are this.
- AllGoal / AnyGoal / SequenceGoal
  Combine child goals with all-must-complete, any-must-complete, or in-order semantics.

Every QuestNode implements the same two questions, so callers never have to know which
kind of node they hold:

```
func is_completed() -> bool
func progress() -> float   # 0.0 .. 1.0
```

Quest just forwards those to its root, and QuestManager forwards them per id
(QuestManager.is_completed(id)), so there is one obvious way to ask.

Quest progress is driven by PersistenceKeys: goals read keys, and completing a quest is
usually a side effect of setting one. The Dialogic additions
(`res://addons/dialogic_additions`) expose quests and keys to timelines, and the Beehave
additions (`res://addons/beehave_additions`) start quests from behaviour trees.
